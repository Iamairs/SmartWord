## T7｜定义 `PatchRangeTool` 批处理索引语义

### 目标

把当前批处理写入中最容易产生歧义的索引问题写清楚，为后续实现修正打基础。

### 涉及文件

- `docs/plan_cur.md`
- 如需补充专项说明，可新建临时设计文档
- 后续实现涉及：`src/SmartWord.OfficeIntegration/Tools/PatchRangeTool.cs`

### 必须回答的问题

1. `paragraph_index` 是相对原始文档快照，还是相对前序操作执行后的实时文档？
2. `affected_paragraph_index` 返回值应采用哪套坐标语义？
3. 批处理某一步失败时，后续步骤是否继续？
4. 是否允许第一版直接收紧为“一个工具调用只建议包含单一写操作”？

### 本轮输出要求

- 文档化结论
- 对应测试口径
- 下一轮实现策略建议

### 当前结论

1. `paragraph_index` 的**当前实现语义**定义为：**相对于该操作真正开始执行时的实时文档状态**，不是相对于整个工具调用开始时的原始快照。
2. `affected_paragraph_index` 的**当前返回语义**定义为：
   - 成功时：返回该操作执行完成后、实际受影响段落在实时文档中的索引。
   - 失败时：返回该操作尝试写入的目标索引，仅用于诊断，不表示该索引处内容一定发生了变更。
3. 批处理某一步失败时，当前版本采用**继续执行后续步骤**的策略，并在 `results[]` 中逐项返回 `success/message/affected_paragraph_index`。
4. 为降低 LLM 推理成本与索引漂移风险，当前阶段的规范性建议改为：
   - **默认一个 `patch_range` 工具调用只做一个写操作。**
   - 仅当多步操作都围绕同一局部、且调用方明确理解“实时索引”语义时，才允许一次调用内包含多个操作。
5. 因此，本阶段不会在代码里临时引入 `indexOffset` 一类补丁式机制，因为那会制造“表面修复、实际语义仍不统一”的新歧义。

### 测试口径

1. 当前阶段如补自动化测试，应按“实时索引、逐步执行、逐步漂移”的口径验证，而不是按“原始快照索引”口径写测试。
2. 结果断言必须区分：
   - 单步成功后的最终索引
   - 失败项返回的是诊断目标索引，不是成功写入证明
3. 宿主手工验证应重点覆盖：
   - `insert_paragraph_after` 之后再次引用后续段落时是否仍符合“实时索引”解释
   - `delete_paragraph` 后后续操作是否按删除后的文档坐标继续执行

### 下一轮实现策略建议

1. 若未来要支持稳定批处理，应优先在专项设计中明确是否切换到“整批以原始快照为坐标”的新契约。
2. 若切换契约，应同步修改：
   - Prompt 说明
   - `PatchRangeTool` 输入/输出文档
   - 单元测试与宿主验证脚本
3. 在新契约落地前，不再鼓励 LLM 生成复杂批处理写入。

### 完成标准

- 不再停留在“知道有漂移风险，但没有统一解释”的状态。

## T8｜定义工具超时语义

### 目标

让 `AgentOrchestrator` 中“工具超时”这件事从模糊实现变成明确契约。

### 涉及文件

- `docs/plan_cur.md`
- `docs/project_cur.md`
- 后续实现涉及：`src/SmartWord.Application/Orchestration/AgentOrchestrator.cs`

### 必须回答的问题

1. 当前超时是“合作式取消”还是“编排层停止等待”？
2. 对写工具而言，若未确认其真正停止，是否允许编排层继续推进下一轮？
3. 当前哪些工具是纯只读、哪些工具进入 COM 写路径后风险更高？
4. 下一轮重构是否要按工具类型区分超时策略？

### 本轮输出要求

- 一份清晰的行为定义
- 对现有双超时设计的替换方向说明
- 对测试和宿主验证的边界说明

### 当前结论

1. 当前实现中的“工具超时”应明确解释为：**编排层在超时时间到达后停止等待该工具结果，并向当前轮次写回一个超时错误。**
2. 这**不等价于**底层工具已经被强制终止，因为当前绝大多数工具只能合作式响应 `CancellationToken`。
3. 因此，当前超时语义本质上属于：
   - 读取工具：`best-effort cancel + stop waiting`
   - 写入工具：`stop waiting + 结果不确定，需要按高风险路径处理`
4. 对写工具而言，只要超时发生，就不能把它解释为“文档一定没改”。这类结果必须视为**状态不确定**，需要用户重新读取或人工确认。
5. 本轮不再把“删掉某个 `Task.Delay`”当成修复超时问题，因为真正的问题不是计时器，而是**宿主侧没有可证明的强制终止机制**。

### 行为定义

1. 当前版本的超时错误，语义统一定义为：
   - 编排层未在限定时间内拿到工具结果
   - 系统已放弃继续等待
   - 不承诺工具线程、COM 写入或后台任务已经真正停止
2. 只读工具超时后，可以在同一任务中继续做保守恢复或回退说明。
3. 写工具超时后，后续专项设计应收敛为：
   - 当前任务不再继续推进新的写操作
   - 必要时引导用户先验证文档现状
4. 当前代码尚未完全实现“按工具类型区分后续策略”，但本轮已经把**语义边界**固定下来，避免后续继续误把“超时”当成“已安全取消”。

### 测试与宿主验证边界

1. 单元测试只能验证：
   - 编排层超时后返回错误
   - 日志与事件是否按约定发出
2. 单元测试不能证明：
   - Word COM 写入已被真正中断
   - Roslyn 脚本在宿主线程上的执行已完全停止
3. 宿主手工验证应重点观察：
   - 写工具超时后 Word 文档是否仍有延迟变更
   - 超时后是否还出现迟到的事件回推
   - 当前 run 是否继续推进新的写操作

### 下一轮替换方向

1. 后续实现应按工具类型拆分超时策略，而不是共享一个统一 timeout 包装。
2. `PatchRangeTool`、`ExecuteScriptTool`、只读检索工具，应分别定义：
   - 等待上限
   - 超时后是否允许继续当前 run
   - 是否必须先做状态回读
3. `ExecuteScriptTool` 的超时治理必须和线程模型专项设计一起处理，不能单独局部修补。

### 完成标准

- 后续编码时不再只围绕 `Task.Delay` / `CancelAfter` 争论，而是围绕明确语义实现。

## T9｜整理 `ExecuteScriptTool` 线程模型设计输入

### 目标

为下一阶段专项设计准备输入，不在本轮直接重写脚本执行模型。

### 需要整理的内容

1. 当前模型里哪些地方发生 UI 线程同步等待
2. 当前脚本持有 Word COM 对象的方式有哪些风险
3. 哪些能力必须保留：
   - 复杂写入后备路径
   - 安全校验
   - 与 `patch_range` 的职责边界
4. 哪些方案明确不采用：
   - 直接把原始 COM 对象借给后台线程长期使用

### 完成标准

- 下一轮可以基于这些输入单独写专项设计文档。

### 当前结论

1. 当前 `ExecuteScriptTool` 的执行路径是：
   - 编排层调用工具
   - `WordApplicationWrapper.InvokeWithActiveDocumentAsync(...)` 把访问切回宿主 UI 线程
   - 在 UI 线程中同步等待 `_scriptExecutor.ExecuteAsync(...).GetAwaiter().GetResult()`
2. 这意味着当前脚本执行的真实特征不是“后台安全执行”，而是：
   - **脚本生命周期与 UI 线程强耦合**
   - 脚本期间宿主 UI 线程可能被长时间占用
   - `CancellationToken` 只能合作式生效
3. 当前脚本直接持有 `WordApp/ActiveDoc/app/doc` 等 Word COM 对象，这些对象默认应继续视为**宿主线程受限资源**，不能被当成可安全借给后台线程长期持有的普通对象。
4. 因此，旧方案里“把 COM 对象直接移到后台线程使用”这一方向，当前阶段明确列为**不采用方案**。

### 下一轮专项设计必须回答的问题

1. 脚本执行是否继续坚持“所有 Word COM 访问都回宿主 UI 线程”？
2. 若要降低 UI 阻塞，是否采用：
   - 先在后台完成脚本编译/分析
   - 再在 UI 线程执行真正 COM 访问段
3. `execute_script` 与 `patch_range` 的职责边界是否要进一步收紧，避免脚本成为常规写入路径？
4. 超时、取消、宿主关闭时，脚本执行状态如何可靠回传？

### 本阶段已固定的约束

1. 不直接把原始 Word COM 对象借给后台线程长期使用。
2. 不在没有专项设计的情况下重做当前线程模型。
3. `execute_script` 仍只作为复杂写入的后备路径，而不是默认写入入口。

2. `SaveSettings()` 原地更新单例的风险边界
3. `SmartWordBridge` 当前运行时依赖 `ServiceLocator` 的具体位置
4. 后续若逐步改造，应如何分批推进而不影响宿主稳定性

### 完成标准

- 下一轮可以按批次推进，而不是一次性大改 DI 路径。

### 当前结论

1. 当前设置模型里同时存在 `ApiBaseUrl` 与 `BaseUrl`，真实运行时又以 `LlmClientOptions.BaseUrl` 为主，这说明这里本质上是**历史兼容字段与当前主字段并存**。
2. `ServiceLocator.SaveSettings()` 当前会：
   - 持久化 `settings.json`
   - 原地更新单例 `SmartWordSettings`
   - 同步把值写回单例 `LlmClientOptions`
3. 这种“原地更新单例”在当前阶段是可接受的折中，但必须明确它的边界：
   - 适合低频设置更新
   - 不适合作为复杂运行时配置热切换框架
4. `SmartWordBridge` / `WebViewBridge` 当前仍直接依赖 `ServiceLocator` 拉取 `IAgentOrchestrator`、`LlmClientOptions`、`WordApplicationWrapper` 与设置快照，因此它仍然是一个**运行时服务定位入口**，而不是纯构造注入对象。

### 下一轮分批推进建议

1. 先统一设置字段主语义：
   - 明确 `BaseUrl` 为内部主字段
   - `ApiBaseUrl` 只保留输入/输出兼容职责
2. 再把设置保存从“直接改多个单例”收敛到一个明确的设置应用服务。
3. 最后才考虑减少 `ServiceLocator` 在 Bridge 层的直接使用，把依赖逐步下沉到可注入组件。

### 本阶段不做的事

1. 不一次性移除 `ServiceLocator`。
2. 不在当前宿主初始化路径中强推全量 DI 重构。
3. 不把设置热更新问题扩大成整套配置中心改造。

## T11｜整理长期对话治理输入

### 目标

把 `InMemoryConversationStore`、`ConversationCompressor` 和 token 估算统一纳入同一主题，而不是零散修补。

### 需要整理的内容

1. 当前存储上限问题
2. 当前 token 粗估策略问题
3. 压缩与存储裁剪之间的关系
4. 哪些问题需要优先改，哪些可以后置

### 完成标准

- 后续上下文治理有统一入口，而不是继续分散在多个任务中。

### 当前结论

1. 当前长期对话治理涉及三个分散点：
   - `InMemoryConversationStore` 只做追加，不做上限裁剪
   - `EstimateTokenCount()` 只是按文本长度做粗估
   - `ConversationCompressor` 仅在单次 run 中压缩上下文，不会反写存储
2. 这意味着当前系统虽然已经具备“本轮上下文压缩”能力，但尚未形成**存储层、估算层、运行层**的一体化治理。
3. 当前最优先的问题不是立刻接入更复杂的存储，而是先明确：
   - 什么时候该裁剪历史
   - 什么时候该压缩摘要
   - 两者的职责边界如何区分

### 统一主题下的职责划分建议

1. 存储裁剪：
   - 负责限制持久层或内存层历史无限增长
   - 目标是控制资源占用
2. 上下文压缩：
   - 负责在单次模型调用前，把长历史收敛成仍可理解的提示上下文
   - 目标是控制推理输入长度
3. token 估算：
   - 负责提供是否需要压缩/裁剪的触发依据
   - 当前粗估可继续保留，但必须标注其不精确性

### 下一轮优先级建议

1. 先改进 token 估算口径，使阈值触发更稳定。
2. 再决定是否把压缩摘要写回存储，避免每次 run 都重复压缩。
3. 最后再考虑长期持久化和跨文档会话治理，不应与当前稳定性修复阶段混在一起。

## T12｜整理 Bridge 显式 COM 接口评估输入

### 目标

为后续是否从 `AutoDual` 迁移到显式接口提供事实基础。

### 需要整理的内容

1. 当前 WebView2 HostObject 的使用方式
2. 显式 COM 接口改造需要验证的互操作点
3. 不应直接采用的未经验证示例写法
4. 哪些收益是确定的，哪些仍需实验验证

### 完成标准

- 后续如要做显式接口收敛，能基于真实约束推进，而不是照抄模板代码。

### 当前结论

1. 当前 `WebViewBridge` 通过 `[ComVisible(true)] + [ClassInterface(ClassInterfaceType.AutoDual)]` 暴露给 WebView2 HostObject，这一实现虽然接口面偏大，但它**当前是可工作的互操作基线**。
2. 因此，本阶段对它的定位是：
   - 这是一个需要评估收敛的问题
   - 不是一个已经证明必须立即迁移的线上故障点
3. 若后续迁移到显式 COM 接口，至少要重新验证以下互操作点：
   - HostObject 是否仍能稳定暴露同步方法和返回值
   - `Task` / `string` / `void` 这类方法签名在前端桥接里的实际表现
   - WebView2 侧调用方式是否需要同步调整
   - 关闭、异常、序列化失败时的回传行为是否有变化
4. 对网上常见“定义接口 + 实现类 + 直接替换属性”的示例，本阶段明确不直接照搬，因为当前项目里还有：
   - VSTO 宿主生命周期
   - WebView2 HostObject 序列化行为
   - WinForms 控件线程切换
   这些真实约束未被那些示例覆盖。

### 收益与风险评估

1. 确定收益：
   - 可以缩小默认暴露的 COM 接口面
   - 有利于长期维护和接口约束清晰化
2. 未验证风险：
   - HostObject 兼容性细节变化
   - 前端桥接调用方式回归
   - 调试与异常行为变化

### 下一轮专项设计建议

1. 先做最小实验验证显式接口方案是否兼容当前 HostObject 调用链。
2. 只有在实验验证通过后，再决定是否正式迁移。
3. 若迁移，必须把前端桥接、错误处理、关闭流程一起纳入回归验证范围。
