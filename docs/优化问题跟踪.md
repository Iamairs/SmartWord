# SmartWord 优化问题跟踪清单

> 更新时间：2026-07-27
> 本文用于记录当前项目仍可优化的问题、处理状态、建议解决方案、当前卡点与验收口径。
> 本次仅做问题登记与治理规划，不代表对应问题已经完成实现。

## 状态口径

| 状态 | 含义 |
| --- | --- |
| 未开始 | 已识别问题，但尚未进入实现。 |
| 进行中 | 已有实现计划或部分代码改动，但尚未完成验收。 |
| 部分完成 | 已具备部分能力，但仍存在明确缺口。 |
| 已完成 | 已完成实现、测试和文档闭环。 |
| 暂缓 | 当前收益、风险或依赖条件不适合近期推进。 |

## 总体判断

当前项目已经具备 Ask / Plan / Agent、工具调用、写入确认、Undo、自动验证、Todo Board、Skill、任务历史和 Benchmark Telemetry 等核心能力。后续优化重点不应继续无序堆功能，而应优先补齐以下基础：

1. 让 Benchmark 的评分结果可信。
2. 建立真实 Word 宿主级验证能力。
3. 降低 Agent 编排层复杂度。
4. 强化写入生命周期、COM 生命周期和脚本安全边界。
5. 将关键 Prompt 约束逐步下沉为代码约束。
6. 改善普通用户对“将要修改什么、已经修改什么、是否验证成功”的理解。

## P0：近期必须处理

### OPT-P0-001：Benchmark Scorer 评分覆盖不足

| 字段 | 内容 |
| --- | --- |
| 状态 | 已解决（保留人工评审边界） |
| 问题 | 当前 benchmark 的 expected.json 已包含页面设置、页眉页脚、样式、表格、编号、不得额外修改等检查，但 scorer 主要覆盖文本和过程事件。正式报告可能高估能力。 |
| 影响 | Benchmark 结果可信度不足，后续优化缺少可靠回归指标。 |
| 建议解决方案 | 引入 ICheckScorer，每种 check type 单独实现；未支持的 check 明确输出 unsupported；报告增加评分覆盖率；优先用 OpenXML 做静态格式判分，必要时再启动 Word COM。 |
| 当前卡点 | `semantic_quality_review` 仍需人工或独立 Judge；OpenXML 无法验证真实分页渲染。 |
| 验收口径 | 所有 expected check 要么可评分，要么明确 unsupported；报告展示覆盖率；unsupported 不计入正式完成率。 |

#### 解决记录 2026-07-26

- 处理状态：已完成当前 `benchmark/cases` 16 个用例的 schema 覆盖。
- 修改范围：`tools/SmartWord.EvalRunner`、`tests/SmartWord.EvalRunner.Tests`、评测报告输出。
- 核心方案：以 OpenXML 快照为主判分源，引入分类型 `ICheckScorer`；确定性检查自动评分，未知/缺证据项返回 `unsupported`，语义质量项返回 `manual_required`。
- 测试验证：EvalRunner 与新增 4 项测试在 `--no-dependencies` 模式构建/执行通过；dry-score 断言所有 expected check 均返回明确状态。
- 剩余风险：OpenXML 不提供 Word 实际分页结果；trace 未记录基准 token 比例时无法自动评分该性能项。
- 后续动作：在具备稳定 Word 环境后补充可选 hybrid scorer；如接入 LLM Judge，仅单独输出 `judge_score`。

| 验收口径 | 未保存文档和另存为场景状态不串；路径变更可迁移或明确提示。 |

### OPT-P1-008：模型能力检测依赖名称规则

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | 当前已支持部分模型能力规则，但主要基于模型名匹配。 |
| 影响 | 供应商变更模型名或协议行为后，工具调用、reasoning_content、usage 解析可能失效。 |
| 建议解决方案 | 连接测试时真实探测工具调用、usage、reasoning_content、并行工具支持；缓存探测结果；允许用户覆盖。 |
| 当前卡点 | 不同 Provider 的兼容协议差异较多，需要抽象 provider adapter。 |
| 验收口径 | 模型能力来自真实探测或明确配置；名称规则只作为 fallback。 |

### OPT-P1-009：上下文预算仍以估算为主

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | 已有上下文压缩和预算策略，但 token 统计、工具 schema 预算、输出预留和压缩保真仍可增强。 |
| 影响 | 大文档和长任务中可能提前压缩不足或压缩过度。 |
| 建议解决方案 | 引入模型级 tokenizer；区分 system/user/tool/reasoning token；硬状态不可丢；工具结果结构化引用；展示成本预算。 |
| 当前卡点 | 不同模型 tokenizer 不统一；兼容 OpenAI-like provider 时真实 token 不一定返回。 |
| 验收口径 | 压缩前后 token 有可观测数据；关键硬状态不会被压缩丢失；超长任务稳定性提升。 |

### OPT-P1-010：关键 Prompt 规则应下沉为代码约束

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | 写后验证、COM 集合不用 foreach、验证属性与写入属性一致等关键规则仍较依赖 Prompt。 |
| 影响 | 模型偶发不遵守 Prompt 时，可能导致脚本失败或验证不严。 |
| 建议解决方案 | 通过 schema、AST 校验、自动验证计划、patch 操作白名单、状态机约束等方式强制关键规则。 |
| 当前卡点 | 需要平衡通用脚本灵活性和安全强约束。 |
| 验收口径 | 关键安全规则即使模型输出错误也会被代码拦截并给出可修复反馈。 |

## P2：产品能力优化

### OPT-P2-001：缺少真实改动 Diff

| 字段 | 内容 |
| --- | --- |
| 状态 | 未开始 |
| 问题 | 写入确认面板主要展示操作摘要，不是真正的前后对比。 |
| 影响 | 用户难以判断即将修改的具体内容，信任感不足。 |
| 建议解决方案 | 文本写入展示字符级 diff；格式写入展示属性差异；表格操作展示受影响行列；原始 JSON 折叠展示。 |
| 当前卡点 | 格式 diff 和 Word 修订/域/表格的差异表达需要设计。 |
| 验收口径 | 用户无需查看技术 JSON 就能理解修改前后差异和风险。 |

### OPT-P2-002：尚未集成 Word 修订模式

| 字段 | 内容 |
| --- | --- |
| 状态 | 未开始 |
| 问题 | 当前主要依赖 Undo 和验证，不能替代合同、论文、报告场景常用的修订痕迹。 |
| 影响 | 专业审阅场景可信度不足。 |
| 建议解决方案 | 设计 SmartWord 写入时是否临时启用修订、是否恢复原状态、验证是否忽略修订标记、接受/拒绝流程如何交给用户。 |
| 当前卡点 | Word 修订模式会影响文档 DOM 与验证逻辑，需要真实 Word 测试。 |
| 验收口径 | 用户可选择用修订模式应用文本改动；任务结束后修订状态可解释、可恢复。 |

### OPT-P2-003：通用脚本依赖偏高

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | execute_script 很强，但长期依赖模型生成 Word COM 代码会带来可靠性和安全成本。 |
| 影响 | 格式、表格、页眉页脚等高频任务稳定性受模型代码质量影响。 |
| 建议解决方案 | 沉淀专用业务工具：format_audit、format_apply、document_health_check、replace_terms、review_comments、normalize_headings、normalize_tables、inspect_page_setup、apply_page_setup。 |
| 当前卡点 | 需要从 Benchmark 和用户高频任务中选择优先工具，不宜一次性覆盖所有 Word 对象。 |
| 验收口径 | 高频任务更多通过 schema 化工具完成，脚本成为后备路径。 |

### OPT-P2-004：选区优先缺少后端硬约束

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | Prompt 已要求选区优先，但写工具仍需要更强的范围校验。 |
| 影响 | 选区类请求可能误扩展到全文或错误段落。 |
| 建议解决方案 | 请求携带 targetScope；SelectionOnly 模式下写工具拒绝越界；写入确认显示是否越过选区。 |
| 当前卡点 | 需要可靠记录选区范围，并在用户操作过程中处理选区变化。 |
| 验收口径 | 选区任务不会修改选区外内容，除非用户明确升级范围。 |

### OPT-P2-005：Plan 缺少可编辑和版本化

| 字段 | 内容 |
| --- | --- |
| 状态 | 部分完成 |
| 问题 | Plan 能生成并进入 Agent，但用户不能充分编辑、删改、重排、锁定和版本化计划。 |
| 影响 | 复杂任务执行前的可控性不足。 |
| 建议解决方案 | 前端 Plan 面板支持编辑步骤、删除、排序、跳过、加约束；执行时记录 plan revision。 |
| 当前卡点 | 需要定义编辑后 ExecutionPlan 与 Todo Board 的映射规则。 |
| 验收口径 | Agent 执行的是用户最终确认版本；任务历史记录 plan revision。 |

### OPT-P2-006：文档体检和自动修复需要分离

| 字段 | 内容 |
| --- | --- |
| 状态 | 未开始 |
| 问题 | 普通用户更适合“先只读扫描，再选择修复”，不适合体检入口直接全自动修改。 |
| 影响 | 产品信任感和可控性不足。 |
| 建议解决方案 | 建立流程：只读扫描 -> 问题清单 -> 用户选择 -> 预览修复 -> 执行 -> 验证。 |
| 当前卡点 | 需要先实现 document_health_check 和基础问题分类。 |
| 验收口径 | 文档体检默认不修改文档；用户选择修复项后才进入写入确认。 |

### OPT-P2-007：引用定位仍偏粗

| --- | --- |

| 影响 | 长段落、表格、批注场景下用户难以定位证据。 |

| 验收口径 | 点击引用可定位到精确文本或单元格；失效时提示用户而不是跳错位置。 |

## 建议落地顺序

近期建议按以下顺序推进，不建议同时开太多线：

1. OPT-P0-001：补齐 Benchmark Scorer 和评分覆盖率。
2. OPT-P0-002 + OPT-P0-003：建立真实 Word 集成测试和 VSTO 构建环境。
3. OPT-P0-005：将写入生命周期抽成显式状态机。
4. OPT-P0-004：在状态机稳定后拆分 AgentOrchestrator。
5. OPT-P2-001：增加真实改动 Diff，提升用户信任感。
6. OPT-P2-003：沉淀高频专用工具，降低对通用脚本的依赖。
