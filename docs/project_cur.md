# 当前需求说明：稳定性修复与高风险设计收敛

## 0. 文档用途

本文件用于描述**当前阶段真正要解决的问题、交付边界、优先级依据和实施约束**。

它回答的是下面几个问题：

1. 现在这轮工作为什么要做。
2. 这轮工作到底做哪些内容。
3. 哪些问题虽然重要，但本轮不能直接动代码。
4. 后续实施时必须遵守哪些架构和验证约束。

具体的实施步骤、依赖顺序、测试安排、分批交付清单，统一写在 `docs/plan_cur.md`。

---

## 1. 当前阶段的背景

基于对 `README.md`、`docs/已实现的功能.md`、`docs/代码评审报告.md` 与 `docs/重构计划.md` 的重新校准，可以确认 SmartWord 当前的整体方向没有问题：

- VSTO Word 插件宿主、WebView2 桥接、Ask 模式只读链路、Agent 模式最小写入闭环已经具备基础可用性。
- 当前最主要的问题不是“架构完全错误”，而是**若干实现细节会影响稳定性、可观测性和后续扩展成本**。
- 旧版评审报告里有一部分问题识别是对的，但存在风险等级过重、证据链不足、修复方案与当前 COM 线程模型冲突等问题。

因此，本轮工作的定位不是“大重构”，而是：

**先修已经确认的稳定性问题，再把高风险设计问题收敛成可评审、可落地的专项设计。**

---

## 2. 当前阶段的总目标

本轮工作的总目标可以概括为四句话：

1. 修掉当前已经确认、且能直接落地的稳定性缺陷。
2. 提升日志质量，减少排障成本和隐私暴露风险。
3. 为上下文治理补齐最小可用能力，避免长对话直接进入语义模糊状态。
4. 对 COM / 线程 / 超时这类高耦合问题，先把契约和设计说清楚，再决定实现方式。

换句话说，这轮不是去追求“能力更多”，而是要让当前 Phase 3 已落地能力**更稳、更可维护、更可继续开发**。

---

## 3. 当前阶段的交付范围

### 3.1 第一类：直接进入实现的稳定性修复

本轮确认要落地的内容包括：

1. `OpenAiCompatibleClient` 改为复用 `HttpClient`
2. `UndoRecordWrapper` 补齐 `UndoRecord` COM 释放
3. `IntentRouter` 改善解析逻辑并补失败日志
4. `ConversationCompressor` 从空实现升级为最小可用版本，并真正接入 `AgentOrchestrator`
5. `WordApplicationWrapper` 诊断日志接入 `Serilog`
6. `OpenAiCompatibleClient` 与 `WebViewBridge` 日志脱敏
7. `WebViewBridge.PostEventToJs()` 关闭阶段保护
8. `WebViewBridge.WaitForToolConfirmationAsync()` 释放 `CancellationTokenRegistration`

这部分是当前阶段的**核心交付范围**。

---

### 3.2 第二类：先明确契约，再进入实现的问题

这部分本轮不直接做大改，但必须先产出明确结论：

1. `PatchRangeTool` 的批处理索引语义
2. `AgentOrchestrator` 的工具超时语义

这些问题虽然已经在评审中被识别出来，但旧版方案都还不够可靠：

- `PatchRangeTool` 不是简单加一个 `indexOffset` 就能根治，前提是必须先明确“索引相对于谁”。
- 工具超时也不是简单删掉 `Task.Delay` 就结束，根本问题在于当前工具大多只能合作式响应取消，不能默认强制终止。

因此，这一类问题本轮要完成的是：

- 补契约
- 补说明
- 补测试口径
- 收敛下一轮的实现方向

---

### 3.3 第三类：专项设计后再决定是否实现的问题

以下内容本轮**不直接进入编码实现**，但要在文档和计划中明确它们的正确定位：

1. `ExecuteScriptTool` 线程模型重做
2. 设置对象与 Service Locator 的长期收敛
3. 长期对话存储与 token 估算治理
4. `WebViewBridge` 显式 COM 接口收敛

原因不是这些问题不重要，而是：

- 它们都和当前宿主线程模型、Word COM 访问约束、HostObject 互操作方式高度耦合。
- 如果没有专项设计，直接照旧版重构建议去改，很容易引入新的线程或互操作问题。

---

## 4. 当前阶段明确不包含的内容

为了保证范围收敛，本轮明确不处理以下事项：

1. Plan 模式采访流程
2. Plan -> Agent 上下文重构
3. SQLite 对话持久化落地
4. Word 宿主级全自动 E2E 测试体系
5. `execute_script` 的新一版线程模型实现
6. `PatchRangeTool` 的复杂表格写入、细粒度格式化、跨段落复杂批处理
7. Bridge 的显式 COM 接口正式迁移

这些内容不是被否定，而是**不属于当前这轮最有效率的交付范围**。

## 6. 当前阶段的关键判断

### 6.1 当前最该优先修的是“确定问题”，不是“想象中的更优架构”

这轮优先级排序必须基于已经核验的事实，而不是基于理想架构：

- `HttpClient` 每次新建是确定问题
- `UndoRecord` COM 未释放是确定问题
- `IntentRouter` 子字符串匹配脆弱是确定问题
- 日志明文过多是确定问题
- 压缩器空实现是确定问题

相比之下，以下问题虽然重要，但现在不能粗暴下手：

- 脚本线程模型
- Bridge 显式 COM 接口化
- Service Locator 完全收口

---

### 6.2 线程与 COM 相关问题不能脱离当前防腐层约束处理

本项目当前已经明确采用了一个核心前提：

**Word COM 访问默认回宿主 UI 线程执行。**

这意味着：

- 不应为了“避免某个同步等待”就把原始 COM 对象直接借给后台线程长期使用。
- 不应在没有专项设计的情况下重做 `ExecuteScriptTool` 执行模型。
- 与 COM 访问相关的修复，必须优先保证宿主线程安全，而不是追求局部优雅。

---

### 6.3 超时问题的本质是“语义不清”，不是“少一段代码”

当前工具超时问题当然要处理，但根因不是单独的 `Task.Delay` 或 `CancelAfter`，而是：

- 编排层到底要承诺什么样的超时语义？
- 已经开始执行的 Word 写操作，是否允许编排层在未确认其真正停止时继续下一轮？
- 当前哪些工具只支持合作式取消，哪些工具可以做到更强约束？

因此，超时问题在当前阶段应该先做：

1. 语义收敛
2. 行为定义
3. 测试边界说明

再决定是否调整实现。

---

### 6.4 `PatchRangeTool` 的核心问题是契约，而不是技巧

旧版计划试图通过 `indexOffset` 解决批量操作的索引漂移，但这只能在“索引语义已经清楚”的前提下成立。

当前必须先回答：

1. `paragraph_index` 是针对原始快照，还是针对实时文档？
2. 批处理某一步失败后，后续是否继续？
3. 返回结果里的 `affected_paragraph_index` 应以哪套坐标系解释？

如果这些问题不先写清楚，那么任何实现都只是把歧义从文档转移到代码里。

## 7. 当前阶段的实施原则

### 7.1 先做小而确定的修改

优先做这种任务：

- 单点缺陷清晰
- 影响面有限
- 可通过单元测试或最小手工验证确认

例如：

- `HttpClient` 复用
- `UndoRecord` 释放
- `IntentRouter` 逻辑修正
- 日志脱敏

---

### 7.2 先补最小可用能力，不追求一步到位

`ConversationCompressor` 当前完全空置，因此第一版的目标不是“智能摘要”，而是：

- 保留系统消息
- 保留最近关键消息
- 插入明确的压缩说明
- 让编排层在阈值触发后仍保持确定语义

这符合当前阶段的成本收益比。

---

### 7.3 文档、测试、实现三者保持一致

本轮最容易出问题的点是：

- 文档里说的是一种语义
- 代码里实现的是另一种语义
- 测试覆盖的是第三种假设

因此，本轮必须坚持：

1. 先把契约写清楚
2. 再改实现
3. 再让测试与契约对齐

---

### 7.4 区分“纯逻辑验证”和“宿主验证”

当前项目是 Word 插件，不可能把所有问题都压成纯单元测试。

因此必须接受并明确区分两类验证：

- 纯逻辑单元测试：解析、压缩、日志摘要、token 估算、路由判断
- Word/宿主手工验证：COM 释放、UI 线程调度、关闭流程、确认回传、任务撤销

## 9. 当前已明确的契约结论

### 9.1 `PatchRangeTool` 批处理索引语义

当前阶段正式采用如下解释：

1. `paragraph_index` 按**实时文档坐标**解释，即每个操作都基于它真正执行时的文档状态定位。
2. `affected_paragraph_index` 在成功时表示**执行完成后的实际受影响段落索引**；失败时仅表示**尝试写入的目标索引**，用于诊断。
3. 同一次 `patch_range` 调用中的多个操作，按给定顺序顺次执行，前一步对文档结构的影响会直接改变后续操作的坐标语义。
4. 某一步失败时，当前版本不会自动停止整批，而是继续执行并返回逐项结果。

这意味着当前代码虽然可支持批处理，但它更接近“脚本式顺序写入”，而不是“基于固定快照的事务性批处理”。

因此，本轮对调用侧的明确要求是：

- 默认一个 `patch_range` 调用只包含一个写操作。
- 若必须批处理，调用方必须显式接受“实时索引可能漂移”的语义。

### 9.2 工具超时语义

当前阶段正式采用如下解释：

1. 工具超时表示**编排层停止等待该工具结果**，不表示工具一定已经被底层强制终止。
2. 当前系统没有可靠机制证明所有 COM 写操作或脚本执行都能在超时点被立即终止，因此“超时”不能被解释成“文档一定未改动”。
3. 只读工具与写入工具必须区别看待：
   - 只读工具超时，主要影响本轮推理完整性。
   - 写入工具超时，会引入“文档状态不确定”的风险。
4. 因此，后续专项实现必须朝“按工具类型定义超时后续策略”的方向推进，而不是继续沿用统一包装。

这意味着当前阶段先收敛的是**语义**，不是贸然声称已经具备“可靠强制取消”能力。

### 9.3 `ExecuteScriptTool` 线程模型设计输入

当前阶段已经确认以下事实：

1. `ExecuteScriptTool` 当前不是后台独立执行模型，而是通过 `WordApplicationWrapper` 回到宿主 UI 线程后，同步等待脚本执行完成。
2. 当前脚本可直接访问 `WordApp/ActiveDoc` 等 COM 对象，因此它天然受 Word COM 线程约束影响。
3. 这条路径的核心价值仍然成立：它是复杂写入的后备能力，也是 `patch_range` 无法覆盖场景的兜底方案。
4. 但它的改造必须建立在“线程模型 + 取消语义 + COM 可见边界”一起设计的前提上。

本阶段已经明确排除的方向是：

- 直接把原始 Word COM 对象借给后台线程长期使用。

下一阶段如要继续推进，只能以专项设计方式处理。

### 9.4 设置模型与依赖注入收敛输入

当前阶段已经确认以下事实：

1. 设置对象同时保留了 `ApiBaseUrl` 与 `BaseUrl`，这是兼容演进遗留，不是理想完成态。
2. `SaveSettings()` 当前采用“写文件 + 原地更新单例设置 + 原地更新 `LlmClientOptions`”的策略。
3. `WebViewBridge` 仍直接通过 `ServiceLocator` 拉取核心运行服务，因此当前体系仍然是“组合根 + 运行时服务定位”混合模式。

这类问题属于长期收敛方向，但它不是当前阶段最该冒险大改的点。下一阶段若推进，应采用**字段语义统一 -> 设置应用服务收口 -> Bridge 依赖收口**的分批方式，而不是一次性重写宿主初始化链路。

### 9.5 长期对话治理输入

当前阶段已经确认以下事实：

1. `InMemoryConversationStore` 当前只做追加，不做存储裁剪。
2. token 估算仍是粗粒度长度估算，只适合触发级判断，不适合精确预算。
3. `ConversationCompressor` 已经可以在单次 run 中压缩上下文，但它还没有与存储层形成统一治理闭环。

因此，下一阶段应把“历史裁剪、上下文压缩、token 估算”作为同一主题推进，避免再次分散成互相独立的小修补。
