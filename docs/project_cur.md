# 当前问题说明

## 背景

SmartWord 当前已具备 Ask / Agent / Plan 三种模式的基础骨架，其中 Plan 模式已经接入：

- `ask_user_question` 采访工具
- `QuestionAsked` / `PlanReady` 事件
- WebView2 问答回传通道
- 前端问题面板与计划面板

但在真实宿主环境中，切换到 Plan 模式并提交问题后，系统表现为“无响应 / 卡住”。现有日志显示：

- 前端请求已进入 `Plan` 模式
- 文档上下文读取成功
- LLM 工具调用响应成功返回
- 最后一条日志停在 `LLM 工具接口响应解析完成... ToolCallCount=3`

说明请求并没有卡在网络层，而是更可能卡在“工具调用结果进入编排器之后”的阶段。

## 当前研判

结合代码与日志，当前优先怀疑以下几个实现缺口：

1. Plan 模式允许模型一轮返回多个工具调用，但编排器在 `ask_user_question` 或写入状态切换时会提前 `break`，同一轮后续 tool call 没有被显式收口。
2. `PLAN.md` 当前允许“每轮至多 3 个问题”，但前端状态只支持一次展示一个 `pendingQuestion`，协议能力与提示词约束不一致。
3. 若模型返回的 `tool_call.id` 为空，前端提交回答时会因为 `questionId` 为空而无法回传，宿主侧会一直等待。
4. 当前关键节点缺少足够日志，导致日志只能看到 LLM 返回了 3 个 tool call，却看不到是否真正进入了提问等待态。

## 修复目标

本次修复的验收标准：

1. Plan 模式收到多 tool call 时，不再因为未收口的剩余调用导致后续链路异常。
2. `ask_user_question` 即使缺少 `tool_call.id`，系统也能生成稳定回传 ID，不再无限等待。
3. 提示词与前端能力对齐，单轮只允许提出一个采访问题，剩余问题必须等待用户回答后再继续。
4. 增补自动化测试，覆盖 Plan 问答链路中的关键异常场景。
5. 更新临时计划文档，并在完成后按需回写功能说明。
