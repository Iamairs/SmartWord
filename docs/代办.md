# SmartWord 产品与架构改进代办

> 本文基于当前代码与文档现状整理，目标是把上一轮产品建议转化为可评审、可排期、可验收的需求池。筛选标准为：可靠性、可实现性、高效性、安全性。  
> 当前结论：SmartWord 的底层 Agent 能力已经较强，下一阶段重点不应继续堆工具，而应把现有能力产品化为用户可理解、可审阅、可撤销、可复用的 Word 工作流。

## 1. 当前代码能力判断

### 1.1 已经具备的架构优势

- **模式与工具边界清晰**：`ToolRegistry` 按 Ask / Plan / Agent 暴露工具，Ask / Plan 只暴露只读工具，Agent 才能执行写入工具。
- **权限模型已有基础**：`PermissionGuard` 支持 `ReadOnly / ConfirmWrites / AutoSafeWrites / FullAuto` 四档权限，且状态写入、文档补丁写入、脚本写入已被区分。
- **写入闭环比较完整**：`AgentOrchestrator` 已有写步骤 Undo、自动验证、验证失败回滚、失败修复、暂停决策等链路。
- **Todo Board 已经可作为执行状态载体**：`TodoManager` 支持运行态、恢复态、暂停态、可信检查点、当前写步骤快照，前端已有 `TodoBoardPanel / RecoveryPanel / PausePanel`。
- **前后端事件协议已经较丰富**：事件已覆盖工具开始/完成、写入执行、验证结果、Todo 更新、PlanReady、QuestionAsked、取消、错误等状态。
- **Word COM 防腐层已有雏形**：`WordApplicationWrapper` 将 COM 调用切回宿主 UI 线程，并在多处显式释放 COM 对象。
- **脚本路径已有安全基础**：`ScriptSecurityValidator` 对受限命名空间、受限标识符、只读脚本写操作做了静态拦截。
- **测试覆盖了关键纯逻辑**：权限、工具 schema、Todo、编排器、压缩、LLM payload 等已有自动化测试基础。

### 1.2 当前产品化短板

- **普通用户仍暴露过多技术概念**：主界面直接呈现 Ask / Plan / Agent、轻量/重量模型、Base URL、工具名和原始 JSON。
- **确认对象偏技术，不偏业务结果**：`ContentPreviewPanel` 当前确认的是工具名和原始输入，尚未让用户看到“将改哪里、改成什么、风险是什么”。
- **改动审阅能力不足**：`ChangesSummaryPanel` 能展示受影响段落和验证状态，但还没有改动前后对比、逐条接受/拒绝、修订模式应用。
- **设置安全性不足**：当前设置通过 JSON 明文持久化，API Key 尚未接入 Windows DPAPI 加密。
- **长期历史仍未落地**：`SqliteConversationStore` 仍是骨架，当前正式注册的是 `InMemoryConversationStore`，任务历史和长期审计无法可靠支撑。
- **无保存文档身份存在碰撞风险**：`JsonTodoStore` 对空文档路径使用 `__active_document__`，多个未保存文档的 Todo Board 容易混淆。
- **脚本沙箱不能被视为强安全边界**：当前 AST 校验能挡住常见危险写法，但 dynamic COM 与 Roslyn 脚本天然难以做到完备隔离。
- **高频 Word 工作流尚未产品化**：选区润色、格式统一、批注处理、文档体检、合同审查等仍主要依赖用户自然语言触发。

## 2. 设计原则

### 2.1 普通用户优先看到任务，不优先看到模式

Ask / Plan / Agent 是内部执行策略。普通用户更关心“总结、润色、审阅、格式整理、处理批注”。短期可以保留模式选择，但应逐步降级为高级选项。

### 2.2 用户确认业务改动，技术详情默认折叠

确认面板、工具轨迹、改动摘要应默认展示自然语言动作和影响范围；工具名、JSON、脚本代码保留在“技术详情”中。

### 2.3 所有自动写入都必须可解释、可验证、可撤销

任何会改 Word 文档的功能都应尽量复用当前写步骤 Undo、自动验证、Todo 检查点和取消链路。不要绕过 `AgentOrchestrator` 私自写 Word。

### 2.4 先做只读诊断，再做自动修复

复杂工作流建议先以只读体检或建议清单交付，再逐步接入可确认修复。这样更可靠，也更容易做测试。

### 2.5 脚本能力保持后备路径，不作为默认产品能力

`execute_script` 对复杂 Word DOM 很有价值，但风险和调试成本高。产品工作流应优先走标准工具、模板化脚本和受控确认。

## 3. P0：应优先处理的基础体验与安全问题

> 完成状态：P0 阶段已完成。对应提交包括 `f312bfa`、`d1925fb`、`a2cf06c`、`49583e0`、`dadad18` 以及最终文档收尾提交。已落地配置诊断、DPAPI 密钥保护、设置基础/高级分层、快捷任务入口、权限说明、业务化写入确认和选区优先快捷操作。

### P0-1. 首次配置向导与模型能力检测

**价值**：降低首次使用门槛，避免用户配置了不支持工具调用的模型后才在任务中失败。  
**可靠性**：高。主要是新增诊断入口，不影响现有主链路。  
**可实现性**：高。已有 `LlmClientOptions.ResolveModelRoute` 和模型能力规则，可补一个轻量测试请求。  
**高效性**：高。提前发现配置问题，减少无效 Agent 运行。  
**安全性**：中高。诊断请求必须避免发送文档内容。

**建议内容**：

- 设置页增加“连接向导”：服务商、Base URL、API Key、模型名、测试连接。
- 服务商预设：OpenAI、Azure OpenAI、DeepSeek/SiliconFlow、Ollama、自定义。
- 测试结果至少区分：连接失败、Key 无效、模型不存在、支持流式、支持工具调用、不支持工具调用。
- 当模型不支持工具调用时，在 UI 中明确提示：只能普通对话，不能读取或修改当前 Word 文档。

**实现提示**：

- 前端：`settings.js`、`ChatWindow.vue` 可先做基础/高级分区。
- 后端：`WebViewBridge` 增加 `TestModelConnection` 类 bridge 方法，或在现有设置保存后触发诊断。
- LLM 层：避免复用真实文档上下文，测试消息使用固定短文本。

**验收标准**：

- 新用户可在 1 分钟内完成基础配置并看到明确可用状态。
- 工具调用不支持时，不允许静默进入 Agent 写入链路。
- 诊断日志不记录 API Key 和测试原文以外的敏感信息。

### P0-2. API Key 本地加密与设置分层

**价值**：当前 API Key 明文写入 `%AppData%\SmartWord\settings.json`，与正式办公产品安全预期不符。  
**可靠性**：高。配置读写是独立模块，可做兼容迁移。  
**可实现性**：高。Windows 桌面插件可使用 DPAPI。  
**高效性**：中。主要提升安全，不直接影响执行速度。  
**安全性**：高。

**建议内容**：

- 使用 Windows DPAPI 加密保存 API Key 字段。
- UI 显示已保存 Key 时只显示脱敏状态，不回显完整 Key。
- 设置页分为“基础设置”和“高级设置”：
  - 基础：服务商、API Key、模型质量档位、权限模式、测试连接。
  - 高级：Base URL、轻量/重量模型、自定义系统指令、调试选项。
- 保留旧明文字段读取兼容，首次保存后迁移为加密格式。

**实现提示**：

- 位置：`ServiceLocator.SaveSettings`、`LoadSmartWordSettings`、`SmartWordSettings`。
- 新增 `SecretProtector` 或类似基础设施类，封装 `ProtectedData.Protect/Unprotect`。
- 前端 `settings.js` 不应持久持有完整已保存 Key，保存后只保留 mask。

**验收标准**：

- 新保存的 Key 不以明文出现在 settings.json。
- 旧明文 settings.json 能继续读取并迁移。
- API Key 不进入普通日志、前端环境提示、错误消息。

### P0-3. 普通用户界面去工程化

**价值**：降低认知负担，让用户先看到“能做什么”，不是先理解 Agent 架构。  
**可靠性**：高。主要是前端展示调整，不改核心 Agent 链路。  
**可实现性**：高。当前 Vue 组件较集中，改造成本可控。  
**高效性**：高。减少用户输入试错。  
**安全性**：中。通过默认推荐安全模式，间接提升安全。

**建议内容**：

- 首页或输入框上方增加快捷任务：
  - 总结全文
  - 总结当前章节
  - 润色选区
  - 压缩选区
  - 扩写选区
  - 检查错别字和病句
  - 统一格式
  - 处理批注
  - 文档体检
- Ask / Plan / Agent 模式切换移动到“高级模式”或折叠区域。
- 初始化欢迎语改为任务导向，不再提示“前端初始化”“WebView2 环境”等技术状态。
- 浏览器预览 / WebView2 环境提示只在调试模式展示。

**实现提示**：

- 前端：`ChatWindow.vue` 可新增 `QuickActionsPanel.vue`。
- 快捷任务初期可直接生成自然语言 prompt 并带上推荐 `manualMode`。
- 高风险快捷任务默认走 Plan 或 ConfirmWrites。

**验收标准**：

- 新用户打开侧边栏能直接看到 6-10 个可点击任务。
- 普通界面不再默认展示 Base URL、WebView2 环境、工具 JSON。
- 仍可在高级设置中手动选择 Ask / Plan / Agent。

### P0-4. 写入确认面板改为“业务改动确认”

**价值**：用户不应确认 `patch_range` 或 `execute_script`，而应确认“将修改哪些内容”。  
**可靠性**：中高。先做展示层改进，后续再做真正 diff。  
**可实现性**：中。`patch_range` 可较容易解析操作；`execute_script` 只能先展示描述和影响范围。  
**高效性**：中。确认更清楚，减少用户取消和误操作。  
**安全性**：高。

**建议内容**：

- `ContentPreviewPanel` 默认展示：
  - 操作目的
  - 影响范围
  - 操作类型
  - 是否可自动验证
  - 是否可撤销
  - 风险等级
- 原始 JSON / 脚本代码放入“技术详情”。
- 对 `patch_range` 解析操作列表，展示“第 N 段替换为……”“第 N 段后插入……”。
- 对 `execute_script` 要求模型提供更具体的 `description` 和 `affected_paragraphs`，否则标记为高风险。

**实现提示**：

- 前端可先在 `ContentPreviewPanel.vue` 中解析 `toolInput`。
- 后端后续可新增结构化 `preview` 字段，避免前端重复解析工具输入。
- `AgentEvent.OperationDescription` 应继续作为用户可读描述的主字段。

**验收标准**：

- 普通用户无需展开 JSON，也能判断是否确认执行。
- 脚本类写入默认清晰提示风险高于标准补丁写入。
- 取消任务、跳过此步、确认执行三种动作语义清楚。

### P0-5. 权限模式解释与默认策略优化

**价值**：当前权限名正确但不够用户化，尤其 `FullAuto` 风险需要更强提示。  
**可靠性**：高。主要是 UI 文案和少量权限校验补充。  
**可实现性**：高。  
**高效性**：中。减少错误配置。  
**安全性**：高。

**建议内容**：

- 权限选项增加说明：
  - 只读模式：不会修改文档。
  - 写入前确认：每次修改前确认，推荐默认。
  - 自动安全写入：标准补丁自动执行，脚本类仍确认。
  - 全自动执行：仅建议在副本或低风险文档中使用。
- `FullAuto` 第一次开启时弹出风险确认。
- 对受保护、只读、强制修订模式文档给出更具体的用户指引。

**实现提示**：

- 前端：`ChatWindow.vue` 的 `permissionOptions` 扩展描述。
- 后端：保留 `PermissionGuard` 当前语义，并补充测试确保 `AutoSafeWrites` 下 `execute_script` 仍需确认。

**验收标准**：

- 默认新用户为写入前确认。
- 全自动执行不会被普通用户误点开启。
- 自动安全写入不会静默执行脚本写入。

### P0-6. 选区优先快捷操作

**价值**：Word 用户最自然的交互是“选中文本后处理”，这是高频低风险入口。  
**可靠性**：高。现有 `get_selection_context` 和上下文水合已有选区信息。  
**可实现性**：中高。初期可用 prompt + Ask/Agent 实现。  
**高效性**：高。减少用户输入。  
**安全性**：中高。默认只处理选区，影响范围小。

**建议内容**：

- 检测到选区时展示选区操作：
  - 润色
  - 压缩
  - 扩写
  - 改成正式表达
  - 解释
  - 翻译
  - 查找风险
- 写入类选区操作提供：
  - 替换原文
  - 插入到下方
  - 仅生成建议
  - 以修订模式应用（后续）

**实现提示**：

- 初期不需要新增后端工具，可复用现有模式和 `get_selection_context`。
- 后续可增加专门的 selection patch 操作，降低段落索引误差。

**验收标准**：

- 有选区时快捷任务优先作用于选区。
- 没有选区时明确提示作用范围，避免误改全文。

## 4. P1：形成可信文档修改闭环

### P1-1. 改动前后对比与审阅中心

**价值**：这是让用户敢用 Agent 修改正式文档的关键。  
**可靠性**：中。需要在写入前后稳定捕获文本和格式摘要。  
**可实现性**：中。文本 diff 可先做，格式 diff 后续扩展。  
**高效性**：中。会增加读写前后的采样，但可控。  
**安全性**：高。

**建议内容**：

- 执行前捕获受影响段落的原文快照。
- 执行后捕获新快照。
- 前端展示改动前 / 改动后，高亮新增、删除、替换。
- 支持跳转到文档位置。
- 后续支持逐条接受 / 拒绝；第一版可以只做审阅展示，不做逐条回滚。

**实现提示**：

- `patch_range` 路径最容易做：操作目标段落明确。
- `execute_script` 路径需要模型或工具提供 `affected_paragraphs`，否则只能展示摘要。
- 可新增 `ChangePreview` / `ChangeSnapshot` 领域模型，由 `AgentEvent` 携带。

**验收标准**：

- 完成任务后用户能看到至少文本级前后对比。
- 对无法生成 diff 的脚本写入，系统明确说明原因和风险。

### P1-2. Word 修订模式集成

**价值**：合同、论文、制度文件用户通常希望留痕，而不是直接覆盖。  
**可靠性**：中。Word 修订模式会影响验证逻辑，需要专门测试。  
**可实现性**：中。可通过 Word COM 控制 `TrackRevisions` 或尊重当前状态。  
**高效性**：中。修订模式可能让验证更复杂。  
**安全性**：高。

**建议内容**：

- 新增应用方式：
  - 直接修改
  - 以修订模式修改
  - 仅生成建议
- 重要文档工作流默认推荐“以修订模式修改”。
- Agent 任务完成后生成“AI 修改摘要”。

**实现提示**：

- 需要扩展 `AgentRunOptions` 或请求参数，明确应用方式。
- `WordApplicationWrapper.GetDocumentStatusAsync` 已读取 `TrackRevisions`，后续可扩展修订控制。
- 验证逻辑要考虑修订文本在 Word DOM 中的表现。

**验收标准**：

- 用户能选择以修订模式应用写入。
- 修订模式下自动验证不会误判常见文本写入失败。

### P1-3. 任务历史与长期审计

**价值**：专业文档修改需要可追踪，尤其是 Agent 自动执行任务。  
**可靠性**：中高。当前 `SqliteConversationStore` 尚未实现，需要补齐持久化。  
**可实现性**：中。已有接口和骨架，但需要 schema、迁移和 UI。  
**高效性**：中。持久化会增加 I/O，但可异步批量写。  
**安全性**：高。要控制敏感内容落盘范围。

**建议内容**：

- 每次任务形成任务记录：
  - 文档标识
  - 用户目标
  - 模式
  - 权限模式
  - 开始/结束时间
  - 工具摘要
  - 改动摘要
  - 验证结果
  - 失败/取消原因
- 前端可查看最近任务、重新运行、继续未完成任务。
- 敏感内容默认摘要化，完整工具输入输出只在调试模式保存。

**实现提示**：

- 实现 `SqliteConversationStore` 或新增 `TaskRunStore`。
- 不建议把所有工具原始输出长期保存为默认行为。
- Todo JSON 可继续承担运行态，SQLite 承担历史态。

**验收标准**：

- 重启 Word 后能看到当前文档最近任务历史。
- 历史记录不会泄露 API Key。
- 可从历史任务跳转到相关段落或查看改动摘要。

### P1-4. 可编辑 Plan 面板

**价值**：复杂任务中，用户需要控制执行步骤，而不是只能接受模型计划。  
**可靠性**：高。Plan 本身不写文档，风险低。  
**可实现性**：中。前端编辑和 ActivePlan 序列化需要补齐。  
**高效性**：高。减少 Agent 走错方向。  
**安全性**：中高。用户显式确认计划可降低误改。

**建议内容**：

- Plan 面板支持：
  - 修改步骤
  - 删除步骤
  - 增加步骤
  - 拖拽排序
  - 标记范围：全文 / 当前章节 / 选区 / 指定标题
  - 设置执行方式：只检查 / 需确认修改 / 可自动修改
- 点击开始执行时传入编辑后的 `activePlan`。

**实现提示**：

- 当前 `ChatWindow.vue` 已有 `activePlan` 展示和 `executePlan`，可在此基础上改造。
- 后端 `TodoManager` 已支持从 `ActivePlan` 重建 Todo Board。

**验收标准**：

- 用户能在执行前调整步骤顺序和内容。
- Agent 执行阶段 Todo Board 与用户编辑后的计划一致。

### P1-5. 文档体检 MVP（只读优先）

**价值**：高频且低风险，是 SmartWord 从聊天工具变成专业文档助手的关键入口。  
**可靠性**：高。第一版只读，不修改文档。  
**可实现性**：中。可复用只读工具，但需要结构化报告 UI。  
**高效性**：中。大文档需要分段读取和预算控制。  
**安全性**：高。

**建议内容**：

- 第一版检查：
  - 标题层级异常
  - 空标题 / 空段落过多
  - 编号疑似不连续
  - 批注和修订未处理
  - 表格数量和大表提示
  - 格式不一致线索
  - 重复短语或明显错别字线索
- 每个问题提供段落跳转。
- 修复按钮后续再接 Agent，不在 MVP 中强制实现。

**实现提示**：

- 先做只读报告工具或工作流，不急于新增写工具。
- 可新增 `document_health_check` 工具，或用现有只读工具由 Agent 生成报告；从可靠性看，专用工具更稳定。

**验收标准**：

- 对中小文档能在可接受时间内生成结构化问题清单。
- 所有问题都能说明证据来源或段落位置。

### P1-6. Todo Board 用户化

**价值**：Todo Board 已经是强能力，但需要从 Agent 内部状态变成用户能监督的执行板。  
**可靠性**：中高。已有后端状态，主要改 UI 和字段映射。  
**可实现性**：中。  
**高效性**：中。减少用户对长任务的不确定感。  
**安全性**：中高。清晰暂停/跳过/继续能减少误操作。

**建议内容**：

- Todo 项展示：
  - 当前阶段
  - 目标范围
  - 修改数量
  - 验证状态
  - 跳过/失败原因
  - 跳转到相关段落
- 支持用户在暂停态选择：
  - 继续当前步骤
  - 跳过当前步骤
  - 停止任务
  - 后续增加：撤回本次任务
- 避免在聊天流里反复插入 Todo 状态，任务板作为独立区域展示。

**实现提示**：

- 前端：`TodoBoardPanel.vue`、`chat.js`。
- 后端：必要时扩展 `TodoBoardItem.Notes` 结构化内容。

**验收标准**：

- 用户能明确知道 Agent 当前正在做哪一步、完成了哪些、失败在哪里。
- 回滚恢复时 UI 明确显示任务板已恢复到可信检查点。

## 5. P2：高价值 Word 工作流

### P2-1. 全文格式统一工作流

**价值**：非常贴合 Word 用户痛点。  
**可靠性**：中。格式属性复杂，必须逐步做。  
**可实现性**：中。可优先覆盖标题、正文、段前段后、行距、字体、字号。  
**高效性**：中高。适合批量脚本，但要模板化。  
**安全性**：中。默认写入前确认或修订模式。

**建议内容**：

- 提供表单化参数：标题样式、正文字体、字号、行距、首行缩进、段前段后。
- 先做只读预检：列出当前不一致项和预计修改范围。
- 再执行可确认修复。

**验收标准**：

- 能处理常见中文文档格式统一。
- 每类格式写什么属性就验证什么属性。

### P2-2. 批注处理工作流

**价值**：论文、合同、评审稿强需求。  
**可靠性**：中。第一版只读汇总可靠，自动处理需谨慎。  
**可实现性**：中。已有 `read_annotations`。  
**高效性**：中。批注数量通常可控。  
**安全性**：中高。

**建议内容**：

- 汇总批注，按作者、章节、风险类型分组。
- 对每条批注生成处理建议。
- 简单批注可一键生成改写候选。
- 自动删除或回复批注应放后续阶段。

### P2-3. 表格整理工作流

**价值**：Word 表格处理高频但复杂。  
**可靠性**：中低到中。合并单元格、跨页表格复杂，应谨慎迭代。  
**可实现性**：中。已有 `read_table`，写入能力需补强。  
**高效性**：中。  
**安全性**：中。

**建议内容**：

- 第一版只做表格读取、摘要、异常提示。
- 第二版做格式类修复：标题行、边框、字体、列宽自适应。
- 对合并单元格复杂表格默认提示人工确认。

### P2-4. 模板与规范库

**价值**：让 SmartWord 从一次性助手变成长期生产工具。  
**可靠性**：中。规范定义需要结构化，否则难测试。  
**可实现性**：中。需要新增规则模型和 UI。  
**高效性**：高。减少每次 prompt 描述。  
**安全性**：中。

**建议内容**：

- 用户可保存当前文档样式为规范。
- 用户可导入公司/学校/期刊模板。
- 规范包括标题、正文、表格、页眉页脚、编号、术语、语气。
- Agent 执行时引用规范，而不是依赖用户每次描述。

### P2-5. 引用和高亮体验增强

**价值**：提升 Ask 和审阅场景可信度。  
**可靠性**：中。段落级已具备，字符级需要补强定位。  
**可实现性**：中。  
**高效性**：中。  
**安全性**：高。

**建议内容**：

- 点击引用后高亮对应段落或字符范围。
- hover 引用显示证据摘要。
- 支持表格、批注引用。
- 修改摘要中点击 Todo 或改动项高亮文档位置。

### P2-6. 错误诊断卡片

**价值**：把技术错误转成用户可操作建议。  
**可靠性**：高。  
**可实现性**：中。需要错误分类映射。  
**高效性**：高。减少用户重复尝试。  
**安全性**：中。

**建议内容**：

- 针对以下错误给出卡片：
  - API Key 无效
  - 模型不支持工具调用
  - 文档只读
  - 文档受保护
  - 文档已切换
  - Word COM 操作失败
  - 脚本安全拦截
  - 验证失败并回滚
- 每张卡片给出“原因、影响、下一步操作”。

## 6. P3：中长期能力

### P3-1. 合同风险审查

高价值但专业风险高。应先做只读风险清单和替代条款建议，默认不直接修改合同正文。需要术语库、规则库、引用证据和免责声明。

### P3-2. 论文/报告规范化

适合在模板与格式统一能力成熟后推进。可覆盖标题层级、摘要关键词、图表编号、参考文献格式、正文语言风格。

### P3-3. 外部参考资料与知识库

需要解决资料导入、引用溯源、隐私边界和 token 成本问题。短期不建议阻塞核心 Word 工作流。

### P3-4. 企业私有化与审计

包括组织模板库、术语库、统一模型配置、敏感文档模式、审计日志、本地模型支持、管理员策略。适合基础产品闭环稳定后推进。

### P3-5. 多文档批处理

复杂度高，涉及文档身份、任务隔离、并发、失败恢复和 UI 批处理队列。建议在单文档任务历史和恢复机制成熟后再做。

## 7. 建议延期或弱化的内容

### 7.1 不建议短期主推全自动执行

`FullAuto` 可以保留给高级用户，但不应作为普通用户主卖点。Word 文档通常价值密度高，产品更应强调“可审阅、可确认、可撤销”。

### 7.2 不建议短期覆盖所有 Word 对象

脚注、域代码、复杂交叉引用、图片版式、复杂嵌套表格等对象容易引入大量边缘问题。短期应优先打透段落、标题、样式、批注、表格基础能力。

### 7.3 不建议把聊天流做成唯一入口

聊天适合表达意图，但审阅、对比、任务管理、设置诊断更适合结构化 UI。应逐步增加任务中心、审阅中心和任务板视图。

### 7.4 不建议默认长期保存完整工具输入输出

完整工具输入输出可能包含敏感文档内容。任务历史应默认保存摘要，完整原始数据只在用户开启调试或企业审计策略允许时保存。

### 7.5 不建议依赖 Prompt 解决所有产品问题

例如改动预览、计划编辑、权限解释、错误诊断、配置检测，都应该由产品和代码状态机承担，不能只靠提示词约束模型。

## 8. 关键技术债与风险修复清单

### T1. 明文 API Key 存储

- **风险**：高。
- **建议优先级**：P0。
- **处理方式**：DPAPI 加密、旧配置迁移、前端脱敏显示。

### T2. 无保存文档 Todo Board 身份碰撞

- **风险**：中高。
- **建议优先级**：P1。
- **处理方式**：对未保存文档引入运行期 document instance id；保存后迁移到真实路径 hash。

### T3. 长期历史未持久化

- **风险**：中。
- **建议优先级**：P1。
- **处理方式**：实现 SQLite 或独立任务历史 store；默认保存摘要。

### T4. 脚本沙箱边界有限

- **风险**：高。
- **建议优先级**：P1 持续治理。
- **处理方式**：脚本类写入默认确认；限制脚本可用 API；扩展安全测试；优先把高频脚本模板化为标准工具。

### T5. 确认面板缺少真实 diff

- **风险**：中高。
- **建议优先级**：P1。
- **处理方式**：先做 patch_range 文本级 diff，再逐步覆盖脚本和格式 diff。

### T6. 上下文与工具调用成本缺少用户可见预算

- **风险**：中。
- **建议优先级**：P2。
- **处理方式**：在任务开始前估算大致耗时/调用量；增加时间、token、工具调用预算提示。

### T7. 只读体检和格式修复缺少专用工具

- **风险**：中。
- **建议优先级**：P2。
- **处理方式**：沉淀 `document_health_check`、`format_audit`、`format_apply` 等专用工具，而不是长期依赖通用脚本。

## 9. 推荐里程碑

### Milestone A：可用性与安全基础

- 配置向导与模型能力检测。
- API Key DPAPI 加密。
- 设置基础/高级分层。
- 快捷任务入口。
- 普通界面隐藏技术环境提示。
- 写入确认面板用户化。

### Milestone B：可信修改闭环

- 改动前后对比。
- 修订模式应用。
- 可编辑 Plan。
- 任务历史 MVP。
- Todo Board 用户化。
- 错误诊断卡片。

### Milestone C：高频 Word 工作流

- 文档体检 MVP。
- 全文格式统一。
- 批注处理。
- 表格审阅与基础整理。
- 引用高亮增强。

### Milestone D：专业化与企业化

- 模板与规范库。
- 合同审查。
- 论文/报告规范化。
- 组织知识库。
- 审计日志与私有化配置。

## 10. 下一步建议

建议先从 **Milestone A** 开始，不直接进入合同审查、知识库、多文档批处理等大功能。当前最值得优先做的是：

1. API Key 加密和配置诊断，先补齐安全底座。
2. 快捷任务入口和设置分层，降低普通用户使用门槛。
3. 写入确认面板用户化，把现有工具能力转成可理解的业务动作。
4. 选区优先操作，快速形成高频使用习惯。

这四项都能复用当前架构，风险相对低，且能明显改善用户第一次使用 SmartWord 的体验。
