# SmartWord 代码评审报告（校准版）

> 评审日期：2026-04-15  
> 评审范围：`README.md`、`docs/已实现的功能.md`，以及 `src/` 下与评审结论直接相关的实现代码  
> 评审方式：基于文档约束的定点核验，不采用“只看现象、不看源码”的推断式结论  
> 说明：本报告替换旧版《代码评审报告》，重点是校准风险等级、补齐证据链，并删除与当前仓库约束不一致的判断

---

## 一、总体结论

SmartWord 当前的整体方向是成立的：

- 分层结构与职责边界总体清晰，和 `README.md` 中定义的架构意图基本一致。
- Ask 模式只读链路、Agent 模式最小写入闭环、WebView2 桥接、日志与配置体系已经具备可持续迭代的基础。
- 当前最需要处理的不是“推倒重来式重构”，而是几项高性价比稳定性修复，以及两项必须先补设计再动手的线程/超时问题。

本次校准后，结论分为三类：

1. 已确认问题：源码已能直接证明，且建议方向明确。
2. 需补设计或补证据的问题：风险方向存在，但旧版报告的定性或修法不够可靠。
3. 不成立或表述失真的结论：与仓库约束冲突，或风险等级明显夸大。

## 二、已确认问题

### 2.1 `OpenAiCompatibleClient` 每次请求新建 `HttpClient`

**文件**：`src/SmartWord.Infrastructure/LlmClients/OpenAiCompatibleClient.cs`

当前实现中，两条主调用路径都在方法内部创建并释放 `HttpClient`：

- `ChatCompletionStreamAsync()`：`new HttpClient()`
- `ChatCompletionWithToolsAsync()`：`new HttpClient()`

这会带来两个直接问题：

- 高频调用下连接复用效果差，网络层抖动会被放大。
- 在 Agent 多轮调用场景中，连接释放与 `TIME_WAIT` 积累会显著增加不稳定性。

**结论**：问题成立，属于高优先级稳定性问题。  
**建议优先级**：`P1`

---

### 2.2 `UndoRecordWrapper` 未释放 `UndoRecord` COM 引用

**文件**：`src/SmartWord.OfficeIntegration/WordWrappers/UndoRecordWrapper.cs`

当前 `BeginTransaction()` 和 `CloseRecord()` 中都直接访问 `_wordApplication.UndoRecord`，但没有释放对应 COM RCW。

这类对象在长时间运行的 Word 插件中不应依赖 GC 做最终回收，尤其是任务频繁执行时。

**结论**：问题成立，属于高优先级资源管理问题。  
**建议优先级**：`P1`

---

### 2.3 `AgentOrchestrator` 的工具超时处理存在缺陷

**文件**：`src/SmartWord.Application/Orchestration/AgentOrchestrator.cs`

当前工具执行逻辑同时使用了两套超时机制：

- `timeoutCts.CancelAfter(ToolExecutionTimeout)`
- `Task.WhenAny(toolTask, Task.Delay(...))`

这至少带来两个确定问题：

- 超时语义重复，逻辑复杂且难以维护。
- 当 `Task.Delay` 先结束时，当前编排流程会把 `toolTask` 视为“已超时”，但原始任务可能仍在后台继续运行。

需要注意的是，这里能**确定**的问题是“存在后台继续运行窗口”，但不能简单写成“所有超时都会导致后台写入污染”。是否真的发生后续写入，还取决于工具是否合作式响应取消、是否已经进入 COM 写路径。

**结论**：问题成立，但应避免绝对化表述。  
**建议优先级**：`P1`

---

### 2.4 `IntentRouter.ParseDecision()` 使用子字符串匹配，且回退分支无日志

**文件**：`src/SmartWord.Application/Orchestration/IntentRouter.cs`

当前实现：

- 使用 `Contains("ask") / Contains("plan") / Contains("agent")` 解析 LLM 返回文本。
- `RouteAsync()` 在 `catch` 中直接回退到关键词路由，但不记录异常。

这会带来：

- 意图词嵌套时的误判风险。
- 路由失败时缺乏诊断信息。

**结论**：问题成立，属于中优先级健壮性问题。  
**建议优先级**：`P2`

---

### 2.5 `ConversationCompressor` 目前是空实现，且尚未真正接入压缩流程

**文件**：

- `src/SmartWord.Application/Context/ConversationCompressor.cs`
- `src/SmartWord.Application/Orchestration/AgentOrchestrator.cs`

当前情况：

- `ConversationCompressor.Compress()` 直接返回原消息。
- `AgentOrchestrator` 在估算超阈值后只发出 `ContextCompacted` 事件，然后停止继续扩展本轮上下文。

这不是“完全无声失败”，因为前端会收到事件；但它确实意味着：

- 当前没有真实压缩能力。
- 上下文到阈值后，任务语义会变得模糊，用户只能得到“停止继续扩展”的结果，而不是一个可继续工作的压缩态上下文。

**结论**：问题成立，属于中优先级能力缺口。  
**建议优先级**：`P2`

---

### 2.6 `PatchRangeTool` 批量操作存在索引语义风险

**文件**：`src/SmartWord.OfficeIntegration/Tools/PatchRangeTool.cs`

当前 `operations` 按顺序执行，但当中包含：

- `insert_paragraph_after`
- `delete_paragraph`

后续操作仍直接使用原始 `paragraph_index`，工具层没有定义“索引是基于原始文档还是基于实时文档”。

因此，风险的本质是：

- 工具契约不完整。
- 在多步写入场景中，LLM 很难稳定构造正确批处理。

这里可以确认“存在风险”，但不能不加定义就直接用“`indexOffset` 补丁”替代设计说明。

**结论**：问题成立，但需要先补契约再改实现。  
**建议优先级**：`P2`

---

### 2.7 `WordApplicationWrapper` 的诊断日志没有接入统一日志体系

**文件**：`src/SmartWord.OfficeIntegration/WordWrappers/WordApplicationWrapper.cs`

当前诊断输出使用 `Trace.WriteLine`，而项目主体使用 `Serilog` 文件日志。

这会导致：

- COM 相关诊断日志无法和主链路日志统一检索。
- 线上问题排查需要同时依赖不同通道。

**结论**：问题成立，属于低风险但高收益的可观测性改进。  
**建议优先级**：`P3`

---

### 2.8 日志中记录了过多原始请求内容，存在隐私与合规风险

**文件**：

- `src/SmartWord.Infrastructure/LlmClients/OpenAiCompatibleClient.cs`
- `src/SmartWord.AddIn/TaskPane/WebViewBridge.cs`

当前日志会记录：

- 前端发送的完整请求 JSON
- LLM 请求体原文
- 错误响应体原文

对 Word 插件这类直接接触用户文档内容的产品而言，这种日志粒度默认偏高。

**结论**：问题成立，属于中优先级合规改进。  
**建议优先级**：`P2`

---

### 2.9 `WebViewBridge.PostEventToJs()` 缺少关闭阶段的对象状态保护

**文件**：`src/SmartWord.AddIn/TaskPane/WebViewBridge.cs`

当前 `PostEventToJs()` 在 `_coreWebView2 != null` 时直接使用 `_ownerControl.InvokeRequired` / `BeginInvoke`，没有先检查：

- `_ownerControl` 是否已释放
- 插件是否处于关闭过程

关闭或切换阶段若后台任务仍在发事件，存在抛出对象释放异常的窗口。

**结论**：问题成立，属于中低优先级关闭路径健壮性问题。  
**建议优先级**：`P2`

## 三、需要补设计或补证据的问题

### 3.1 `ExecuteScriptTool` 的线程模型存在风险，但旧版“必现 STA 死锁”结论证据不足

**文件**：

- `src/SmartWord.OfficeIntegration/Tools/ExecuteScriptTool.cs`
- `src/SmartWord.OfficeIntegration/Scripting/CSharpScriptExecutor.cs`
- `src/SmartWord.OfficeIntegration/WordWrappers/WordApplicationWrapper.cs`

当前实现确实存在风险点：

- 在 `InvokeWithActiveDocumentAsync()` 回到 UI 线程后，同步等待 `_scriptExecutor.ExecuteAsync(...).GetResult()`。
- 脚本又持有原始 Word COM 对象。

但旧版报告把它直接定性为“经典 UI 同步上下文死锁必现”，证据并不充分。原因是：

- `CSharpScriptExecutor.ExecuteAsync()` 内部对 `CSharpScript.RunAsync()` 使用了 `ConfigureAwait(false)`。
- 因此不能简单套用“所有 `await` 延续都会回到 WinForms 同步上下文”的模板化结论。

真正需要强调的是：

- 当前脚本执行模型与“所有 COM 访问必须回 UI 线程”这一包装器设计并不完全一致。
- 旧版重构方案提出“把 `RawApplication` 和 `ActiveDocument` 借给后台线程直接用”，这会直接破坏当前 COM 防腐层的核心约束，因此不能照做。

**结论**：风险方向成立，但旧版定性过满，旧版修法不可直接采用。  
**建议处理方式**：先做线程模型设计，再做实现。

---

### 3.2 `UndoRecordWrapper.ExecuteOnUiThread()` 的死锁风险需要真实场景验证

**文件**：`src/SmartWord.OfficeIntegration/WordWrappers/UndoRecordWrapper.cs`

当前实现使用：

```csharp
_wordApplicationWrapper.InvokeAsync(action).GetAwaiter().GetResult();
```

这确实意味着后台线程会同步等待 UI 线程执行完成，但是否会形成循环等待，取决于同时是否存在“UI 线程反向等待当前后台线程”的场景。

从现有代码片段本身，只能证明“同步等待增加了线程耦合风险”，还不能直接提升到高危死锁缺陷。

**结论**：风险存在，但需要复现或更完整的调用链证据。  
**建议处理方式**：保留观察项，等脚本线程模型与任务收尾路径一起评审。

---

### 3.3 `SaveSettings()` 的“原地突变单例”值得优化，但当前更像设计债务而非立即缺陷

**文件**：

- `src/SmartWord.AddIn/DI/ServiceLocator.cs`
- `src/SmartWord.Infrastructure/Configuration/SmartWordSettings.cs`

当前 `SaveSettings()` 在 `SettingsSyncRoot` 锁内：

- 写文件
- 修改 `SmartWordSettings` 单例实例
- 修改 `LlmClientOptions` 单例实例

这在设计上不够优雅，也会提高后续并发推理复杂度；但旧版报告直接把它写成“已出现数据竞争”，证据不足。

可以确认的是：

- `ApiBaseUrl` 与 `BaseUrl` 的双字段兼容成本确实存在。
- 单例实例原地更新会增加未来维护复杂度。

**结论**：属于中长期设计改进项，不建议和高优先级稳定性修复混在同一批次处理。

---

### 3.4 `InMemoryConversationStore` 的上限与 token 估算问题真实存在，但紧迫性低于当前稳定性问题

**文件**：`src/SmartWord.Infrastructure/Persistence/InMemoryConversationStore.cs`

当前实现：

- 队列没有上限。
- token 估算采用简单的 `字符数 / 2`。

这两点都会影响长期运行体验，但结合当前项目阶段与已实现功能范围，它们更适合放在“上下文治理专项”里统一处理，而不是插队到当前第一批修复里。

**结论**：问题方向成立，优先级低于网络、COM 释放和线程模型问题。

---

### 3.5 `CancellationToken.Register()` 的释放问题应修，但不应夸大为主要内存泄漏来源

**文件**：`src/SmartWord.AddIn/TaskPane/WebViewBridge.cs`

当前确认等待路径中确实没有释放 `CancellationTokenRegistration`。这会导致闭包在该 token 生命周期内被额外持有。

但结合当前实现：

- 请求级 `CancellationTokenSource` 会在 `SendMessageAsync()` 的 `finally` 中释放。

因此这里更准确的表述应是：

- 存在一次请求生命周期内的多余引用保留。
- 值得修复，但不是当前最主要的泄漏源。

**结论**：问题存在，但旧版优先级偏高。

## 四、不成立或表述失真的旧结论

### 4.1 “AddIn 直接依赖 Infrastructure 违反依赖方向规则”不成立

`README.md` 已明确给出允许的依赖方向：

```text
AddIn → Application → Core
AddIn → OfficeIntegration → Core
AddIn → Infrastructure → Core
```

因此，`SmartWordBridge` 直接解析 `LlmClientOptions` 可以批评为：

- 可测试性一般
- 运行时路径使用 Service Locator

但不能写成“架构越界”。

---

### 4.2 “`async void InitializeTaskPane()` 会直接导致 Word 进程崩溃”表述失真

当前 `InitializeTaskPane()` 虽然采用 `async void`，但方法体内部已经用 `try/catch` 包住异步初始化过程，并且会记录错误日志。

因此更准确的结论应是：

- 这是一个不够理想的实现方式。
- 改成 `Task` 返回值更利于测试与生命周期编排。
- 但不能直接定性为当前实现中“异常必然失控并崩溃进程”。

---

### 4.3 “`AutoDual` 直接构成安全漏洞”表述过重

`[ClassInterface(ClassInterfaceType.AutoDual)]`` 确实会扩大 COM 暴露面，长期来看不利于接口收敛与演进。

但就当前上下文，更准确的结论是：

- 这是一个可维护性和接口控制问题。
- 是否要改成显式 COM 接口，需要结合 WebView2 HostObject 的真实约束做专项验证。

不宜在没有验证前直接标成主要安全缺陷。

---

## 五、建议的修复优先级

### 第一批：可以直接进入实施

1. 复用 `HttpClient`，取消每次请求新建实例。
2. 在 `UndoRecordWrapper` 中补齐 `UndoRecord` COM 释放。
3. 收敛工具超时逻辑，并明确“当前超时是否为合作式取消”。
4. 修正 `IntentRouter` 解析逻辑并补日志。
5. 对 LLM 请求日志与前端请求日志做脱敏。
6. 将 `WordApplicationWrapper` 诊断日志统一接入 `Serilog`。
7. 给 `PostEventToJs()` 增加关闭阶段保护。

### 第二批：先补设计再实施

1. `ExecuteScriptTool` 的脚本线程模型重设计。
2. `PatchRangeTool` 的批处理索引契约与回滚语义。
3. 上下文压缩和长期对话治理。
4. 设置对象更新策略与运行时依赖注入收敛。

---

## 六、最终评价

项目当前最重要的问题不是“架构崩坏”，而是几项具体实现需要校准：

- 有些旧结论方向对，但等级过重。
- 有些旧修复方案本身会破坏当前 COM 线程约束。
- 有些真正值得优先处理的问题，反而适合用更小、更稳的方式先落地。

因此，后续应以“先修确定问题，再补高风险设计”作为主线，而不是按旧版报告直接顺序施工。
