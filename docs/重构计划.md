# SmartWord 重构计划（校准版）

> 基于《代码评审报告（校准版）》制定  
> 目标：优先解决已确认稳定性问题，避免引入与当前 VSTO / COM 线程模型冲突的新方案  
> 原则：小步快跑、原子提交、先定义契约再改实现

---

## 一、计划修订原则

旧版计划的主要问题不是“方向完全错误”，而是把几类性质不同的任务混在了一起：

- 能直接修的实现缺陷
- 需要先补契约的工具语义问题
- 需要重新设计线程模型的架构问题

校准后的计划按以下原则执行：

1. 所有 Word COM 访问继续遵守当前防腐层约束：默认回宿主 UI 线程执行。
2. 不采用“把原始 COM 对象借到后台线程直接操作”的方案。
3. 对批量写入和超时治理，先明确语义，再修改实现。
4. 单元测试只覆盖纯逻辑或可隔离逻辑；涉及 Word 宿主、WebView2、COM 调度的项，必须配合手工验证或集成验证。

## 二、阶段一：可直接落地的稳定性修复

### Task 1｜复用 `HttpClient`

**文件**：`src/SmartWord.Infrastructure/LlmClients/OpenAiCompatibleClient.cs`

**目标**：

- 去掉每次请求内部 `new HttpClient()`
- 使用进程级共享实例
- 保持 `HttpRequestMessage` 仍为逐次创建与释放

**实施要点**：

- 使用共享 `HttpClient` 实例。
- 不把认证头写入 `DefaultRequestHeaders`，仍按请求设置，避免不同配置切换时互相污染。
- 保持请求 URI 为显式绝对地址，避免与运行时可变 `BaseUrl` 产生隐式耦合。

**验证方式**：

- 单元测试或最小集成测试验证请求构造逻辑未回归。
- 高频多轮请求下手工观察调用稳定性。

---

### Task 2｜补齐 `UndoRecord` COM 释放

**文件**：`src/SmartWord.OfficeIntegration/WordWrappers/UndoRecordWrapper.cs`

**目标**：

- `BeginTransaction()` 与 `CloseRecord()` 中获取到的 `UndoRecord` 对象都显式释放。

**实施要点**：

- 在局部变量中接收 `UndoRecord`。
- 使用 `finally` 调用 `Marshal.ReleaseComObject`。
- 保持现有日志与异常兜底方式，不同时重写整个 `UndoRecordWrapper` 生命周期。

**验证方式**：

- 运行相关单元测试。
- 在 Word 中重复执行多轮 Agent 写入任务，确认撤销链路正常。

---

### Task 3｜修正 `IntentRouter` 解析与异常日志

**文件**：`src/SmartWord.Application/Orchestration/IntentRouter.cs`

**目标**：

- 避免 `Contains("ask") / Contains("plan") / Contains("agent")` 带来的误判。
- 在 LLM 路由失败回退时补日志。

**实施要点**：

- 优先改为更严格的词边界匹配，或只接受明确结果。
- `catch` 中记录 `Warning` 日志，再回退到关键词路由。

**验证方式**：

- 增加纯逻辑测试，覆盖混合短语、大小写、空响应、异常回退。

---

### Task 4｜接入最小可用的上下文压缩

**文件**：

- `src/SmartWord.Application/Context/ConversationCompressor.cs`
- `src/SmartWord.Application/Orchestration/AgentOrchestrator.cs`

**目标**：

- 不再让 `ConversationCompressor` 保持空实现。
- 超阈值时进入“压缩后继续运行”或“明确终止且告知用户”的单一语义。

**实施要点**：

- 第一版不追求 LLM 摘要，可采用“保留系统消息 + 最近 N 条消息 + 压缩说明占位”的最小实现。
- `AgentOrchestrator` 必须真正调用压缩器，而不是只发事件后停止扩展。
- 压缩策略要保留最近的工具调用结果，避免破坏当前轮推理链。

**验证方式**：

- 增加纯逻辑测试，覆盖压缩触发、保留消息顺序、系统消息保留、摘要占位插入。

---

### Task 5｜统一诊断日志并做脱敏

**文件**：

- `src/SmartWord.OfficeIntegration/WordWrappers/WordApplicationWrapper.cs`
- `src/SmartWord.Infrastructure/LlmClients/OpenAiCompatibleClient.cs`
- `src/SmartWord.AddIn/TaskPane/WebViewBridge.cs`

**目标**：

- `WordApplicationWrapper` 改用 `Serilog`。
- 前端请求和 LLM 请求日志从“记录原文”改为“记录摘要”。

**实施要点**：

- 保留请求关键元数据：模式、模型、消息条数、长度摘要、工具数量、状态码、TraceId。
- 不再默认输出完整请求体、完整用户输入和完整文档片段。
- 错误响应体如需保留，也应增加长度截断或按环境级别控制。

**验证方式**：

- 手工发起 Ask/Agent 请求，检查日志中仍能定位问题，同时不出现大段明文内容。

---

### Task 6｜补关闭阶段保护与确认等待资源释放

**文件**：`src/SmartWord.AddIn/TaskPane/WebViewBridge.cs`

**目标**：

- 关闭或切换阶段不再因为事件回推访问已释放控件而抛异常。
- 确认等待路径释放 `CancellationTokenRegistration`。

**实施要点**：

- `PostEventToJs()` 在访问 `_ownerControl` 前检查是否已释放。
- `BeginInvoke` 回调内再次做一次对象状态检查。
- `WaitForToolConfirmationAsync()` 中保存注册句柄，并在任务完成后释放。

**验证方式**：

- 手工测试：发起长任务后立即关闭侧边栏或结束插件流程，确认不出现关闭期异常。

## 三、阶段二：先补契约再修改实现

### Task 7｜明确定义 `PatchRangeTool` 的批处理索引语义

**文件**：`src/SmartWord.OfficeIntegration/Tools/PatchRangeTool.cs`

**目标**：

- 明确 `operations[*].paragraph_index` 的解释方式。

必须先在文档和测试里回答两个问题：

1. 后续操作的索引是基于“原始文档快照”还是“前序操作后的实时文档”？
2. 当某一步失败时，工具是否继续执行后续步骤？

**实施顺序**：

1. 先补工具契约说明与测试用例。
2. 再决定是否采用 `indexOffset`、重新定位、或拆成“每次只执行一个写操作”的更保守策略。

**说明**：

在契约未定义之前，不建议直接套用旧版计划中的 `indexOffset` 代码模板。

---

### Task 8｜重新定义工具超时语义

**文件**：`src/SmartWord.Application/Orchestration/AgentOrchestrator.cs`

**目标**：

- 解决当前双超时逻辑混杂的问题。
- 明确“工具超时”到底是：
  - 合作式取消
  - 编排层停止等待
  - 还是宿主层强制终止

**当前约束**：

- 现有工具并不是都能被真正强制中止。
- 特别是已经进入 Word COM 写路径的操作，不能简单依赖 `CancellationToken` 保证停止。

**建议方案**：

第一步先做语义收敛，而不是直接上复杂中止机制：

1. 删掉重复超时设计，避免同一层既 `CancelAfter` 又 `Task.Delay`。
2. 文档中明确“当前超时是合作式的还是仅停止等待”。
3. 对写工具和脚本工具单独评估是否允许编排层在未确认工具已停下时继续推进下一轮。

**说明**：

这个任务应在 `ExecuteScriptTool` 线程模型设计前后联动处理，不能孤立修改。

## 四、阶段三：需要重新设计的架构问题

### Task 9｜重做 `ExecuteScriptTool` 的线程模型

**文件**：

- `src/SmartWord.OfficeIntegration/Tools/ExecuteScriptTool.cs`
- `src/SmartWord.OfficeIntegration/Scripting/CSharpScriptExecutor.cs`
- `src/SmartWord.OfficeIntegration/WordWrappers/WordApplicationWrapper.cs`

**目标**：

- 让脚本执行模型与当前 COM 防腐层一致。
- 避免“脚本直接持有原始 Word COM 对象并在不透明线程上下文中调用”。

**不采用的方案**：

- 不把 `RawApplication`、`ActiveDocument` 直接借给后台线程长期使用。

**建议方向**：

1. 脚本运行环境只暴露受控 API 或受控上下文对象。
2. 需要操作 Word 时，通过包装器显式回 UI 线程。
3. 脚本线程模型、超时模型、权限模型一起设计，而不是单点修补。

**交付要求**：

- 先输出专项设计文档。
- 评审通过后再进入代码实现。

## 七、最终说明

本计划不再把“高风险猜测”直接转成“立即编码任务”。

执行原则改为：

- 先修已经确认的问题。
- 对 COM / 线程 / 超时这类会相互耦合的任务，先收敛语义，再动实现。
- 用最小修改面换取最稳定的收益，避免在 Word 插件宿主里做未经验证的大重构。
