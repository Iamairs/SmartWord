# SmartWord 用户向 README 重写规格

## 需求背景

现有根目录 `README.md` 主要承担内部开发规格索引职责，包含实现伪代码、类名、工具协议、提示词约束和安全实现细节，不能直接作为终端用户、部署人员和新贡献者的统一入口。需要结合当前源码、`docs` 文档和 Git 历史，重写为与实际能力一致、可公开阅读的项目说明。

## 目标

1. 说明 SmartWord 的产品定位、当前可用能力、适用场景和已知边界。
2. 提供安装前提、配置方式、构建验证和基本使用流程。
3. 以用户能理解的语言说明 Ask/Plan/Agent、权限、确认、撤销、验证、Skill 和数据存储行为。
4. 明确 README 的公开信息边界：用户需要知道的行为与风险写入 README；内部实现、提示词、工具 JSON、类级架构和评测细节留在 `docs/`、`specs/` 或代码中。
5. 保留面向开发者的最小贡献入口，但不将内部设计文档伪装成产品承诺。

## 修改范围

- 重写根目录 `README.md`。
- 新增本 spec 文档。

## 不在范围

- 不修改产品代码、前端代码、构建脚本或配置默认值。
- 不承诺当前尚未实现的功能（如完整 Diff、修订模式、在线 Skill 市场、OS 级强沙箱）。
- 不在 README 中复制完整系统提示词、工具 Schema、COM/Roslyn 伪代码或内部评测数据。

## 实现方案

- 以当前 `src/`、`web/`、`tests/` 和 `build.ps1` 的实际结构为准，修正文档中过时的项目名称和能力描述。
- 从 `docs/已实现的功能.md` 提取已落地的用户能力；从 `docs/instructions/` 提取必要的行为约束与边界；从 Git 提交记录确认近期 Skill、遥测、构建和真实 Word 测试能力。
- README 采用“产品介绍 → 能力 → 安装配置 → 使用 → 数据与安全 → 开发验证 → 文档边界”的结构。

## 测试计划

- 使用 UTF-8 检查 README 内容与链接、命令和项目路径的一致性。
- 运行与文档变更匹配的只读校验：检查文件存在、关键命令和目录名称；不因纯文档变更强制运行 Word 集成测试。
- 查看 `git diff --check`，确认无空白错误。

## 风险与注意事项

- README 面向用户的表述必须区分“已实现”“实验性/受限”“计划中”。
- API Key、文档内容、任务历史和本地路径等隐私行为需说明，但不得写出真实密钥或内部日志样例。
- VSTO AddIn 不能用 .NET SDK 自带 MSBuild 构建，必须保留 `build.ps1` 入口说明。
