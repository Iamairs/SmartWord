# 修复 LLM HTTPS 握手失败

## 需求背景

SmartWord 在 Word VSTO 宿主中调用 SiliconFlow OpenAI 兼容接口时，`HttpClient.SendAsync` 抛出“未能创建 SSL/TLS 安全通道”。系统 `curl` 与 PowerShell 5.1 可以访问同一 HTTPS 地址，说明网络、DNS 和服务端证书并非整体不可用。现有 `OpenAiCompatibleClient` 使用默认 `HttpClientHandler`，未明确 TLS 协议；在共享 `WINWORD.EXE` 进程中，其行为可能受到 Word、其他 AddIn 或系统旧默认值影响。

## 目标

- 为 LLM 客户端显式启用 TLS 1.2，避免依赖 Word 进程的隐式 TLS 默认值。
- 将配置限定在 SmartWord 自有 `HttpClientHandler`，不修改进程级 `ServicePointManager.SecurityProtocol`。
- 保持现有共享 `HttpClient`、SSE 流式读取、超时、重试和请求协议不变。
- 增加回归测试，锁定 TLS 协议配置与进程级无副作用约束。

## 修改范围

- `src/SmartWord.Infrastructure/LlmClients/OpenAiCompatibleClient.cs`
- `tests/SmartWord.Application.Tests/Infrastructure/OpenAiCompatibleClientTlsTests.cs`
- `docs/已实现的功能.md` 中的网络兼容性说明

## 不在范围

- 不关闭证书校验，不接受无效或自签名服务器证书。
- 不修改 API Key、模型路由、请求 JSON、SSE 解析或前端协议。
- 不写入系统 TLS 注册表，也不修改 Word 进程的全局安全协议。
- 不将真实 SiliconFlow 请求作为自动化测试依赖。
- 不调整当前网络异常重试次数。

## 实现方案

1. 新增专用 `CreateHttpClientHandler` 方法，在 `HttpClientHandler.SslProtocols` 上设置 `SslProtocols.Tls12`。
2. `CreateSharedHttpClient` 使用该 Handler 创建共享客户端，继续保持无限总超时，由现有分阶段超时机制控制请求。
3. 增加中文注释，说明局部 Handler 配置用于隔离 Word/其他 AddIn 对进程级 TLS 状态的影响。
4. 单元测试通过反射构造 Handler，断言启用了 TLS 1.2，并断言构造前后 `ServicePointManager.SecurityProtocol` 未变化。

## 测试计划

- 运行新增 TLS 测试。
- 运行 `SmartWord.Application.Tests` 全量测试。
- 构建 `SmartWord.Infrastructure`。
- 使用仓库 `build.ps1 -AddIn` 构建 VSTO AddIn，确认 .NET Framework 4.7.2 真宿主编译通过。
- 用 `curl --tlsv1.2 --tls-max 1.2` 验证目标服务当前接受 TLS 1.2，仅作为环境诊断，不作为单元测试。

## 风险与注意事项

- TLS 1.2 是 .NET Framework 4.7.2 与主流 OpenAI 兼容服务之间的稳定交集；仅支持 TLS 1.3 的服务仍无法由当前技术栈访问。
- `HttpClientHandler.SslProtocols` 必须由当前 .NET Framework 4.7.2 reference assemblies 支持，需通过 Infrastructure 和 AddIn 构建验证。
- 企业 HTTPS 检查或代理证书不受本修复覆盖；证书链异常仍应正常失败，不能绕过校验。
- 原工作区存在 BenchmarkScorer 等未提交改动，本任务在独立 worktree 中精准暂存，禁止混入无关文件。
