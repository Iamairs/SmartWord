# SmartWord 用户 README 产品入口重构规格

## 需求背景

上一版 README 虽然整理了仓库能力，但仍以维护者和开发者为主要读者，包含项目状态、开发约定、信息边界、项目结构和大量限制性说明，削弱了产品吸引力和可读性。用户 README 的职责应是让潜在用户快速理解价值、让首次使用者完成配置、让重要文档用户理解可控性，而不是复述内部规格。

## 目标

- 以用户任务和收益为首屏入口，突出 SmartWord 在 Word 内“理解文档、处理选区、执行修改、验证结果”的完整体验。
- 用场景化语言呈现能力，减少 Ask/Plan/Agent、VSTO、COM、工具名等内部术语。
- 将安装与首次使用压缩为清晰路径；开发构建内容单独收敛到贡献者附录或移除。
- 只保留用户必须知道的限制、安全提示和数据处理说明，不暴露内部实现策略。

## 修改范围

- 重写根目录 `README.md` 的全部用户叙事结构。
- 保留并更新现有任务 spec，不修改产品代码。

## 不在范围

- 不在 README 展示“项目状态”“开发约定”“文档与信息边界”等维护者章节。
- 不承诺尚未落地的安装包、完整 Diff、修订模式、跨设备同步或 OS 级强沙箱。
- 不复制内部提示词、工具 Schema、数据库结构、遥测字段或源码级架构。

## 叙事方案

采用以下顺序：一句话价值主张 → 三步体验 → 典型任务 → 核心能力 → 安全与可控性 → 首次配置 → Skill 扩展 → 常见问题 → 开发者入口。用户可在前几屏内判断“这是什么、能做什么、是否敢用、如何开始”。

## 测试计划

- UTF-8 读取 README，检查 Markdown 标题、链接、代码命令和项目路径。
- 运行 `git diff --check`。
- 仅做文档一致性校验，不运行与代码无关的完整构建或 Word 集成测试。

## 风险与注意事项

- 所有“自动”“安全”“可撤销”表述必须带有实际边界，避免形成过度承诺。
- 面向用户的限制应使用行动建议表达，例如“重要文档请先复制”，而不是列出内部失败类型。
- 开发者所需的构建入口可以保留为简短链接或末尾折叠式入口，但不能主导产品 README。
