# Prompt 与 Tool Schema 场景化加固规格

## 需求背景

SmartWord 的 Word Agent 面对长文档、选区编辑、批量格式处理和写后验证等场景。仅依赖自然语言 Prompt 容易出现工具误选、读取范围过大、0/1 基索引混淆、JSON 字段类型错误、批量写入后的索引漂移以及写入后未验证等问题。为了让“工具调用失败率下降”的面试表述有真实工程依据，需要进一步把关键规则落到 Prompt、Tool Schema、输入校验和契约测试中。

## 目标

- 让模型能根据 Word 场景选择最小、最准确的工具链。
- 用 Schema 明确范围、索引、操作顺序、验证要求和危险参数。
- 对高频错误提供可执行的结构化诊断，减少盲目重试。
- 通过 Prompt 合同测试和输入校验测试证明改动有效。

## 修改范围

- `src/SmartWord.AddIn/Resources/Prompts/*.md` 中与工具选择、读取范围、写入和验证相关的规则。
- OfficeIntegration 工具的输入 Schema/Description，以及必要的解析错误信息。
- Application/OfficeIntegration Prompt 与 Schema 契约测试。

## 不在范围

- 不改变 Word COM 操作语义、权限等级或已有公共 Bridge 协议。
- 不虚构失败率数据；本次补充可复现的场景约束和测试证据，指标仍以既有评测口径为准。
- 不把完整工具 JSON 或内部实现细节写入用户 README。

## 场景与方案

1. 长文档事实问答：按“结构探测→关键词定位→局部读取”约束范围，避免全文读取和重复调用。
2. 选区润色：优先读取选区，要求明确目标范围；无选区时先说明范围不确定，不得静默改全文。
3. 批量格式统一：同类操作合并为一次结构化 patch，明确 0-based 索引和实时文档顺序，避免插入/删除后沿用旧索引。
4. 复杂脚本写入：要求写入脚本与验证脚本成对提交，验证属性必须对应写入属性；脚本失败返回结构化诊断。
5. 写后验证失败：验证结果必须包含 expected/actual/hint，模型先读取失败对象再修复，不能重复原调用。

## 测试计划

- Prompt 合同测试验证上述场景规则和禁止项存在。
- Tool Schema 合同测试验证必填字段、类型、枚举、索引约定、验证契约和安全描述。
- 运行 Application/OfficeIntegration 相关测试项目。
- `git diff --check` 和 UTF-8 读取校验。

## 风险与注意事项

- Prompt 规则应短而可执行，避免与现有规则冲突。
- Schema 描述要解释“何时使用”和“何时不要使用”，不能只写字段名称。
- 运行时校验是最终防线，Prompt 不应被当作安全边界。
